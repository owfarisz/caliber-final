Verdict: **changes required**. No critical findings; four important findings below. ## Important findings

1. **Import publication never publishes reviewed analytical data.** `lib/domain.ts:104-106` stores normalized rows in `importBatches` and changes exception labels only. `material()`, `asset()`, stock initialization, and all downstream reads continue to use the original Dataset (`lib/domain.ts:59-69`). A valid new material cannot be requested or reordered after publication; accepting a changed source value does not affect an analytical view or published dataset version. The report explicitly acknowledges this limit, but it conflicts with PRD `docs/PRD-v2.md:157-164`, `:363-365`, and M1 `:448`: history/current records feed the baseline, reviewed batches publish analytical views, and source decisions determine accepted data. The command also has no structured source-row/original-value/transformation/acceptance metadata required at PRD `:203-214` and `:791`; `source` plus normalized rows is insufficient lineage. Add an accepted-source projection/version and provenance/decision contract consumed by readers, while retaining the correct rule that historical imports do not replay against opening physical stock. This is a domain/data-contract gap, independent of absent UI.

2. **Successful origin/hash no-ops do not reserve their idempotency keys.** `lib/domain.ts:86` and `:104` return before the key registry at `:118`. After request origin A already exists, submitting A with a fresh key K returns successfully; reusing K with a different origin B then creates B instead of rejecting mismatched reuse. Duplicate import hashes have the same hole, including cross-command reuse. The report documents the exception, but TRD `:26` and DOMAIN_CONTRACT promise mismatched replay rejection without this exception. Persist a fingerprint/result for every accepted command, including entity/file deduplication no-ops, without creating duplicate business records.

3. **An issue becomes permanently uncorrectable once it has ever had a return.** `lib/domain.ts:97` checks for any ledger row with `issueId === original.id`, rather than an outstanding, unreversed return. Example: issue I → return R → reverse R → reverse I. Reversing R correctly restores net issued quantity, but the immutable R row (and its reversal) still matches the guard, so reversing I always fails with “Reverse linked returns before reversing original issue.” This blocks the correction order that the error itself requests and PRD `:351`/TRD `:37` require. Check active/net return effects, preserve historical entries, and allow the original issue reversal after every linked return has been reversed.

4. **Saved scenario snapshots alias mutable command input/output.** `lib/domain.ts:103` shallow-spreads or assigns the payload into state. `input` and `output` remain the caller's objects. Mutating `payload.input` or `payload.output` after `SaveScenario` therefore changes stored scenario evidence without a command, workspace version, or audit event. Cloning the prior state at `:79` does not clone new payload references. Clone or freeze the saved input/output (also check nested request evidence) so PRD `:265`, `:787` and TRD `:41` isolated/frozen snapshot semantics hold.

- Stock formulas correctly separate physical/reserved/available/inbound and subtract approved outstanding demand once. Draft PRs are excluded from inbound; confirmed amendments retain one PO. Receipt, issue, return quantities and own/other reservations are guarded; effective-date stock validation prevents borrowing from a later receipt. The linked correction case above remains missing.
