# ROOTSYNC v2 — Technical Requirements Document

Status: implementation-ready staging design. Source: docs/PRD-v2.md (all sections) and docs/PRD-DECISIONS.md. Approved execution context: user requests comprehensive TRD before auto implementation.

## Objective and invariants
Exactly Inventory and Technician roles, distinct routes, one browser-local transactional SQLite workspace. Demonstrate condition evidence → isolated scenario → confirmed request → approval/reservation → shortage PR → dated PO → receipt → issue. Every state-changing command requires role, idempotency key, expected workspace version and reason where material. Main must remain deployable and unchanged.

## Architecture
Reuse React/TypeScript, audited seed SQLite (raw + normalized case tables), 7,481-material projection, deterministic intermittent inventory engine, RootSync palette and equipment models. A new `StagingWorkspace` replaces the v1 shell on stagging only. UI invokes a shared domain command service, never mutates stock arrays directly. Pure domain functions are unit-testable. A SQL.js browser adapter stores normalized operational tables plus a versioned aggregate projection and exports the full SQLite including source history. IndexedDB stores the exported bytes after a successful command; state is only exposed as saved when durable serialization succeeds. A failed save retains the previous state and displays an error.

GitHub Pages static routes under `/caliber-final/stagging/`: inventory, inventory/materials, inventory/transactions, inventory/procurement, inventory/data; technician, technician/scenarios, technician/requests. Build emits directory index files and assets with absolute staging prefix. History/popstate and identity restore choose correct workspace. Main deployment artifact combines main and stagging builds, never substitutes staging at root. Source also supports static Vercel hosting; server APIs are optional transport for the shared calculation function, not required to make browser mutations real.

## Shared domain contract
`Role = 'Inventory' | 'Technician'`. Actor ID is demo-inventory or demo-technician; command layer checks role independently of menus.
`WorkspaceState` holds version, epoch, asOfDate, scope; requests with immutable origin + revision and lines; reservations; PRs; POs; ledger; policy/master overrides; observations; maintenance; verification; import batches/exceptions; scenarios; audit; command-key results. Seed stock stays in Dataset, never replay historical issues.
`initializeWorkspace(dataset: Dataset): WorkspaceState` creates empty operational ledger, seed quality records and no imported open PO.
`applyCommand(state: WorkspaceState, dataset: Dataset, command: Command): WorkspaceState` validates all fields before returning a new version; throws typed Error on forbidden, stale, invalid or inconsistent command. Same idempotency key+same payload returns original result/state without another mutation; mismatched replay rejects.
`Command = {type,role,actor,idempotencyKey,expectedVersion,payload}`. `payload` is discriminated by command type. Dates ISO YYYY-MM-DD or UTC timestamp; IDs strings; finite positive quantities, EA/SET integer increments, others decimal allowed to configured precision.
`stockPosition(state,dataset,materialId)` returns onHand, reserved, available, inbound, commitments, position. Physical onHand = seed onHand + receipt + return + adjustment − issue − reversal effects. Available = onHand − active reservations. Position = onHand + remaining confirmed inbound − outstanding approved commitments. Reservations never subtract twice from position.
`requestFulfillment` computes physical progress separately from approval; partial approval and partial issue remain distinct.
`timePhasedReadiness` sorts approved needs and confirmed arrivals by effective date; late inbound cannot cover earlier demand, earlier date's available balance excludes later receipts. Demand origin is unique; unapproved scenario candidates never become operational demand.

## Command specification
Submit/reviseRequest (Technician): asset and BoM-compatible material(s), finite qty, future/on-date needBy, rationale, confirmed scope, origin scenario/revision/task and evidence. Editing only Draft/Needs Clarification; revision increments and resubmits, stable origin duplicate opens existing request. Approval is not an issue.
ReviewRequest (Inventory): Submitted/Under Review → Approved, Partially Approved, Rejected or Needs Clarification; per-line approved qty within requested, mandatory review reason, release reservations if remaining scope is rejected. Never auto-cancel confirmed POs.
Reserve/releaseReservation (Inventory): quantity <= available and unfulfilled approved line. Recheck latest stock/version. No stock movement.
ProceedReorder (Inventory): validate qty/material/date/reason; link request or policy origin; create or amend one draft PR, never duplicate pending action, never count draft as inbound. ConfirmDemoPO requires supplier, confirmed qty and ETA; entered unit price/currency optional with unknown-cost status. It closes/amends PR linkage and adds dated remaining inbound only.
PostReceipt (Inventory): confirmed PO, qty <= remaining, actual effective date; update PO received, ledger, audit atomically. PostIssue: approved line, qty <= outstanding and own reservation + unreserved availability; consume entitlement and update fulfillment/ledger together, physical stock >=0. PostReturn: original issue, qty <= not-yet-returned; append linked movement and adjust fulfillment so returned parts are not still counted as issued. PostAdjustment: signed finite quantity, reason, date; resulting physical and available stock nonnegative. Correction/reversal is a linked opposite entry, original stays immutable, no reversal that violates source/request balances.
AcceptPolicy/master edit (Inventory): immutable ID/UoM; min>=0,max>=min,strategic floor retained, reason and active-policy version. Store imported vs active vs recommended separately.
RecordObservation (Technician): defined metric, asset applicability, unit/bounds, timestamp, source manually entered; no duplicate sample IDs. RecordMaintenance: activity/start/end/failure mode/action/followup, optional linked issue IDs; no stock mutation; no-material activity is valid. RecordVerification: separate reference/log and measured or entered sample; completion alone never normalizes condition.
PublishImport (Inventory): hash deterministic file identity; preview six dataset kinds and required keys/numbers/UoM/FKs; duplicate file is no-op; changed existing business values staged as conflicts, no silent overwrite. Publish valid raw/normalized batch atomically without replaying historical demand against opening stock. ResolveException requires explicit disposition/source/reason; no automatic guessed fills.
SaveScenario: Technician isolated input/output/revision/baseline/workspace/hash; no stock or commitment mutation. Advancing demo date is Inventory-controlled, audited, cannot go backwards. Reset requires explicit confirmation, new epoch and seed state, invalidating prior contexts.

## Browser durability
SQL.js WASM loads from the site prefix. Download canonical demo.sqlite, retain source tables and material projection. Add workspace_meta and normalized operational tables (requests, request_items, reservations, demo_prs, demo_pos, demo_movements, observations, maintenance_logs, verification_records, active_policies, import_batches, data_decisions, scenario_records, audit_events, command_keys). Working aggregate is serialized in workspace_meta for deterministic restoration; normalized tables are materialized transactionally from that same state, not independently edited.
Each command is applied to a clone, persisted into a candidate database inside BEGIN/COMMIT, exported, written in a single IndexedDB transaction, then swapped into the live adapter. Failure leaves the live state unchanged; any candidate DB is closed. One navigator.locks exclusive owner; another tab is read-only with a visible message. Unsupported lock environments are read-only rather than unsafe last-write-wins. Reload restores persisted bytes with seed/schema version check. Export uses the active database, not seed. Reset swaps to clean seed only after user confirmation.

## Monitoring and scenario engine
Choose existing mapped pump PX_PP-1155C and a heat-exchanger asset with useful BoM. Synthetic 30-day condition samples are seeded by asset+metric+date, not copies of prior RootSync readings. Metric definitions include unit/measurement type/applicability/baseline/bounds/attention limit/limit source and freshness window. Pump/compressor: velocity vibration mm/s and bearing temperature degC; exchanger: pressure differential bar and thermal performance %. Other families get Unknown unless configured samples/observations exist. Monitoring condition, material readiness and action state are independent.
Readings display source and event time. Future observations excluded at replay date; missing and >configured-freshness samples remain Unknown/Stale. Play/pause advances replay cursor without writing events. Manual observations append immutable evidence. Existing notifications remain unclassified context, not failures. Maintenance calendar recurrence is nominal until a confirmed execution log exists.
Scenario inputs: asset, horizon 7/30/90/180 days, runtime0–24 (rotating), load80–110% vs configured reference (rotating), throughput80–110% (exchanger), maintenance/cleaning delay0–60d, assumed progression multiplier0–3, supply delay0–180d; advanced holding rate0–100%, price proxy opt-in, cost currency, intervention cost and conditional downtime cost. These are provisional demo envelopes, visibly sourced to configuration.
Shared simulate(dataset,state,input) returns frozen version/hash/input fingerprint, condition series baseline/changed/mitigation with intervals as assumption range, conditional threshold/intervention window (not failure date), failureProbability:null, component candidates/alternative explanations, BoM candidate requirements with unconfirmed scope, coverage and policy, three cost alternatives. Stable input+seed+baseline yields same results. Editing inputs or any relevant state version marks results stale until Run.
Runtime/load/fouling/maintenance assumptions drive class-specific projection coefficients. Maintenance mitigation affects condition progression; buying stock affects readiness only. No universal 120% production multiplier. Need quantity is technician-confirmed, not installed quantity. Unconfirmed lines do not enter commitments. No-part cleaning remains a valid intervention.
Costs: same horizon/currency/opening state; average projected on-hand holding + incremental purchase + intervention + conditional shortage downtime exposure. Separate conditional exposure from calibrated expected cost. Unknown price/currency produces unavailable totals and Review, never zero. Shared-event downtime counted once across missing parts. No FX aggregation. Compare unchanged current plan, changed/no action, changed+mitigation.
